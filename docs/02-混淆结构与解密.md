# 02 · 混淆结构与解密

目标样本：`bundle.js`，约 2.8 MB。

## 混淆方案

`obfuscator.io` 风格的「字符串表 + 双解密器 + 多级包装」。

| 组件 | 名称 | 说明 |
|---|---|---|
| 字符串表 | `_0x453d()` | 返回 **33594** 项字符串数组 |
| RC4 解密器 | `_0x1464(idx, key)` | 索引 `t -= 0` 查表，key 作 RC4 密钥 |
| Base64 解密器 | `_0x43ec(idx, key)` | 同上，改为 Base64 解码 |
| 二级包装 | 1511 个 `function _0xXXXX(e,t,i,s,r)` | 把实参换算成 `(索引, 密钥)` 再调解密器 |

## 三层调用形态

```js
// 第一层：解密器（缓存写入点在逗号表达式内）
const o = t + i[0], n = e[o];
return n ? r = n : (..., r = _0x1464.YwUeqm(r, s), e[o] = r), r;

// 第二层：包装函数（1498 个，形态完全统一）
function _0x1031c6(e, t, i, s, r) { return _0x1464(r - -874, e); }
//                     ↑索引参数   ↑密钥参数  ↑偏移 -874 → +874

function _0xa152(e, t, i, s, r) { return _0x43ec(t - 701, s); }
//                                    ↑偏移 701 → -701

// 第三层：调用点
_0x1031c6("2SSe", 0, 0, 0, -833)      // key 是字符串字面量
_0x24a1d0(0, 0, 17480, 7427)           // pIdx=3, pKey=2, offset=+811 → idx=8238
```

**参数规律**：包装函数一律 5 个形参 `(e,t,i,s,r)`；
`argsExpr` 恒为 `参数-偏移,参数` 两段式，索引偏移可正可负。

## 二次变换

表项本身还会被 `.split("").reverse().join("")` 反转还原，例如：

```js
"xoSySObIcVOWOo8g2T7W".split("").reverse().join("")
```

## 解密方法对比

| 方法 | 做法 | 结果 |
|---|---|---|
| 静态求值（采用） | 抽出表函数+解密器+包装函数，在 Node 中分别求值 | **5361/5361 全部成功** |
| 运行时打桩 | 在浏览器里 hook 解密函数返回值 | 覆盖率低，且易被业务代码异常中断 |
| 暴力穷举 | 索引 × 全部候选 key | 4 亿次组合，不可行 |

### 静态求值的关键坑

1. **解密器必须与字符串表一起加载**
   解密器内部调用 `_0x453d()`，单独 `new Function` 会抛
   `ReferenceError: _0x453d is not defined`，导致**全部求值失败且不报错**。

2. **调用点参数可能是字符串**
   RC4 的 key 常是字符串字面量（`"2SSe"`），正则若只匹配数字会漏掉
   大量调用点（本例中字符串 key 占相当比例）。

3. **包装函数名不一定匹配 `^_0x[0-9a-f]+$` 的直觉**
   实际存在 `_0x43ec`（含数字 `3`）、`_0xa152`（`a`+`1`+`5`+`2`）等形式，
   提取正则要按实际样本设计。
